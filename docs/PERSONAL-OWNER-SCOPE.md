# Personal owner collection contract

The formal release target is Client 0.2.2 over HTTPS. 0.2.3 is only a synthetic isolated upgrade fixture. Source preparation does not deploy, publish a release, issue an invitation or install credentials.

A reviewed grant may use `ids` equal to `{"memory":"personal-owner","rule":"personal-owner","skill":"personal-owner"}`. This complete three-kind marker requires exactly `scopes:["read","put"]`. It names the authenticated owner's fixed personal collection, including future IDs; it is not a filesystem wildcard. Partial markers, rule/skill `*`, remove, write aliases and additional grant fields are rejected. Existing exact-ID grants and the legacy memory `*` remain unchanged and are never automatically expanded.

The Server pins PersonalPolicy root/origin/branch/actor and ContentPolicy digest, and requires these policies for owner grants. Catalog/read/put use server-derived paths and validated typed IDs. Client-supplied actor, root, branch, owner or path fields are rejected. Owner tokens cannot call legacy memory/admin methods or delete content. Each device enrolls independently and can be revoked independently.

Creating a Rule/Skill through an ordinary personal read/put device requires `enabled:false`. Updates must preserve the existing enabled value; Server checks this against the current record inside the write lock, after CAS and before mutation. The same guard applies to existing exact HTTPS read/put grants. Separately reviewed legacy migration/activation grants retain their existing behavior; no new activation API is exposed. Rule trigger modes, Skill paths, dependency allowlists, foreign native files and cache ownership checks still apply. Enabled Rule/Skill body/resource updates are allowed: changes can affect other devices' agent instructions after refresh and context reload. Sync never executes stored scripts or installs dependencies.

Device-local refresh discovers new authorized IDs from the shared catalog without invitation reissue. New disabled Rules remain stored/readable; new disabled Skills are not installed. Enabled existing content maps only into the approved owned namespace. Existing request IDs, durable journal, CAS, conflict retention and offline outbox bindings continue unchanged. A new scope/profile must not adopt or delete an old bound queue: reconcile under its old identity or an explicitly reviewed handoff first. The existing catalog/snapshot safety limits (256 records, 512 KiB) remain; exceeding them blocks refresh without discarding data and requires a separately reviewed pagination change.

Invitations and pending enrollment expire after 300 seconds in the rollout plan. Active tokens currently have no automatic expiry; they remain valid until explicit per-device revoke. A leaked owner token exposes all this owner's shared Memory/Rule/Skill, permits creation and versioned updates including enabled content bodies, and can therefore influence other devices. CAS and budgets are not protection against an authenticated malicious editor. It cannot directly execute Server commands, manage grants or read other configured data roots. Revocation prevents subsequent Server access but does not erase downloaded content or loaded model context; audit the journal/Git, restore affected versions and refresh/reload devices. Server stores token hashes; credentials stay in the native OS credential item and internal Authorization header, never tool arguments or conversation.

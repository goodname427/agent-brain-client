# 并发启动与采集证据

## 已定位的源码缺陷

此前固定启动器在启动 MCP worker 前同步执行 `ClientReleases.update()`。更新检查持有 `update.lock` 和共享的 `python-write.lock`，每个锁默认可等待 20 秒，随后还可能执行 Git 网络检查和候选包健康检查。Onboarding 更新与新会话竞争时，握手会排队等待；锁超时还会拒绝服务。这个机制可用合成环境重现，但不证明此前某次设备握手失败就是锁竞争。

MCP 与正式 Hook 启动器现在都先选取完整校验的稳定不可变包；Hook 仍不检查更新，MCP 握手不等待更新检查。每个启动进程最多安排一次后台检查；非阻塞的 `startup-check.lock` 加绑定原策略摘要的 60 秒时间标记协调同一缓存的启动批次。标记只记录检查尝试，不表示渠道已检查成功或已是最新版。后台检查不等待其他更新持有的锁；显式检查／更新与安装验收仍同步执行原事务。

旧更新器在健康检查前就可能发布候选活动指针。`serving_active()` 同时核对更新 journal 和指针，未完成事务只允许选择已验证的前版，首次安装没有前版则不启动；读取跨越事务变化、文件损坏或未知 journal 状态时明确要求正常重连。校验仍覆盖原策略、manifest、文件哈希和平台 preflight，不放宽信任锚、能力或凭据源码 pin。安装登记检查也使用同一稳定快照，覆盖启动器、租约内检查及 Windows worker；登记、MCP 表、固定入口包与安装回执所有权仍逐项校验。损坏的未完成候选不会被当作登记损坏阻止健康前版，登记漂移仍拒绝启动。选定的 worker 不热切换；后台成功更新只影响未来 worker。宿主退出可以中断后台检查，原 journal 恢复流程仍适用。

此修改需要交付固定启动器及其依赖。仅发布 MCP 活动包不能替换已安装的旧固定入口。源码合入、发布、设备更新和实机验收分别报告。

普通 `update` 在 Mac 和 Windows 均先用原安装事务交接旧固定启动器，再激活新包；离线子进程检查必须能读取原活动包，原 policy、信任锚、固定解释器、暂停状态及其他 MCP 配置保持原样。本次分层源码只接受当前执行布局，0.3.0 专用兼容桥接已删除；旧安装可重新安装。中断后重试同一入口恢复已有 journal。

同一 update 入口还会安装或刷新全局 Hook，并自动登记和开启本设备所有项目的今后会话采集，包含旧设备和非交互更新。复用现有身份及服务，不补传历史；保留数据、队列、排除目录与隔离规则。代码 pin 与 inline command 沿用现有事务恢复；check-update 只报告状态。连接或登记失败保留原采集配置，重跑同一 update 恢复，不要求再次批准摘要或手填 profile ID。正常宿主 Hook 审核仍由用户处理。

## 诊断与证据边界

- 连接未完成初始化：`handshake / mcp-not-ready`。
- 当前 worker 没有提供某个工具：`tools-ready / tool-not-exposed`。核对 `tools/list` 与安装授权；工具缺失本身不能证明 Server 宕机。
- 工具已提供但读取失败：沿用既有 HTTP、传输、解析、远端错误与内容校验阶段；不将其归为工具未提供。
- 内容工具返回 `client_runtime.service_mode=approved-content`，表示工具所属内容服务，不能代替认证、采集或提炼证明。独立 synthetic sandbox 的成功不能证明正式服务成功。
- Hook outbox 的 `confirmed`、`core-accepted` 和事件 `committed` 只确认事件接收。`pipeline_state=unverified`、`model_extraction_verified=false` 明确表示模型提炼尚未确认；不能据此声称已有可查记忆。
- 对“刚才／本轮记录”的问题，需要匹配本轮的唯一标记，或在来源可用时核对事件、会话和发生时间。旧主题及 `memory_updated_at` 不能证明本轮采集成功；找不到证据就报告本轮未确认。

以上来源约束同时写入 MCP instructions 与读取工具描述；它不改变已加载的服务端 Skill，也不代表已验证真实模型一定遵循指引。初始化时的原生映射／身份访问仍有各自的失败与恢复边界；本回归隔离验证的是更新协调及 MCP 协议，不把合成结果扩大为所有启动阶段的端到端保证。

## 合成验证

`tests/test_startup_concurrency.py` 使用隔离 HOME／USERPROFILE／CODEX_HOME、真实启动子进程及 MCP JSON 管道。阻塞合成发布源后，验证单会话、第二会话及 onboarding 更新加两个并发会话的 initialize 和 tools/list；检查同一批次只有一次发布源读取，更新后旧 worker 保持原版本，新 worker 选择新版。另覆盖未健康候选、首次安装无前版、读取竞争、包损坏、健康失败回滚、策略绑定冷却和握手／工具诊断。

同样的两个握手用例在未修改的 `52407ff` 上均超过 5 秒测试预算；这只是受控阻塞下的失败证据，不是实际设备的超时测量。修复后用例无需放开发布源阻塞即可完成握手。

事件回归继续使用原 Hook／outbox 类和合成回执，验证接收确认不会变成提炼确认。Mac 全套发现与 Windows Python 3.11／3.13 CI 显式执行新增并发模块。测试不读取真实记忆、不调用真实模型、不访问设备凭据、不复跑真实事件；用户设备上的正常新会话及真实模型使用验收另列。

## Windows 缓存权限兼容

全局采集旧入口先用普通 `mkdir` 创建 outbox 缓存，Windows 忽略 POSIX `0700` 并继承父目录 ACL；后续 `private_mode` 却只接受固定几个主体。已有缓存、暂存文件或持久锁带其他合法主体时也会在实际读写前被拒绝。设备报告的 `Windows item accessible to another principal` 与这条链路吻合，但缺少该设备实际 ACL 和 Hook 堆栈，不能断言它是唯一原因。

Windows 内容缓存现在交由系统决定实际读写权限，不再用主体名单作为准入门槛；缓存创建、暂存、队列、锁、worker 租约和安装状态读取使用同一边界。新建缓存目录、文件和锁沿用 Windows 原生继承权限，避免创建时又用固定主体名单覆盖系统／宿主授权；已有目录和锁的 ACL 不改写，不重置队列。文件类型、链接／reparse 检查、请求摘要、策略／身份绑定、原请求重试与并发互斥保持。凭据、代码包及配置策略仍走原严格校验，Mac 原行为保持。

原生 Windows 回归从已有普通目录和额外 ACL 出发，通过正式全局 Hook 暂存提示、生成离线 pending 事件、重启并重试原请求，核对原目录／锁 ACL 和已有资料保留。全局 Hook 错误的 stderr 增加 `operation_stage` 和 `error_type`，只报告阶段／类型，不输出正文或原始异常文本。

统一版本交付后最少实测：沿原入口更新一次；完成一个带唯一标记的新会话；检查这轮 `hook-turns` 和 outbox 的原请求及回执。若仍为空，保留现有状态并读取对应 Hook stderr 的阶段／类型；无需手改 ACL、重装、清空队列或补传历史。事件接收与模型提炼／召回分别核验；默认 Memory Query 的 `-32700` 属于独立问题，本修复不宣称解决。

## Codex 旧采集队列自动恢复

正常 Stop Hook 先处理本轮采集，再机会式重试同来源的一条旧 pending 事件。每次保留原 request_id、event_id、时间和正文，经原队列身份绑定、当前 scope／停止开关、隐私标记与 Server admission 核验后提交；复用服务端幂等回执，不生成替代事件。轮转游标只控制下次候选，不修改事件队列内容。失败保留 pending，blocked／conflict／confirmed 不自动重试，本轮失败事件也不会立即重复发送。

恢复设置五秒尝试预算，不超过外层请求剩余预算；队列锁和网络超时使用剩余预算，当前采集优先。网络栈的 DNS 等系统阻塞不承诺硬实时截止。此处没有后台常驻任务，长期闲置来源需后续正常 Hook 或显式 `global-sync` 才继续；MCP 重载、普通刷新和 `global-status` 不会补传。confirmed 仅证明接收回执，不证明提炼正确、GitHub 备份或自动召回。隔离回归见 `tests/test_codex_capture_recovery.py`。

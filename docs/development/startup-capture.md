# 并发启动与采集证据

## 已定位的源码缺陷

此前固定启动器在启动 MCP worker 前同步执行 `ClientReleases.update()`。更新检查持有 `update.lock` 和共享的 `python-write.lock`，每个锁默认可等待 20 秒，随后还可能执行 Git 网络检查和候选包健康检查。Onboarding 更新与新会话竞争时，握手会排队等待；锁超时还会拒绝服务。这个机制可用合成环境重现，但不证明此前某次设备握手失败就是锁竞争。

MCP 与正式 Hook 启动器现在都先选取完整校验的稳定不可变包；Hook 仍不检查更新，MCP 握手不等待更新检查。每个启动进程最多安排一次后台检查；非阻塞的 `startup-check.lock` 加绑定原策略摘要的 60 秒时间标记协调同一缓存的启动批次。标记只记录检查尝试，不表示渠道已检查成功或已是最新版。后台检查不等待其他更新持有的锁；显式检查／更新与安装验收仍同步执行原事务。

旧更新器在健康检查前就可能发布候选活动指针。`serving_active()` 同时核对更新 journal 和指针，未完成事务只允许选择已验证的前版，首次安装没有前版则不启动；读取跨越事务变化、文件损坏或未知 journal 状态时明确要求正常重连。校验仍覆盖原策略、manifest、文件哈希和平台 preflight，不放宽信任锚、能力或凭据源码 pin。安装登记检查也使用同一稳定快照，覆盖启动器、租约内检查及 Windows worker；登记、MCP 表、固定入口包与安装回执所有权仍逐项校验。损坏的未完成候选不会被当作登记损坏阻止健康前版，登记漂移仍拒绝启动。选定的 worker 不热切换；后台成功更新只影响未来 worker。宿主退出可以中断后台检查，原 journal 恢复流程仍适用。

此修改需要交付固定启动器及其依赖。仅发布 MCP 活动包不能替换已安装的旧固定入口。源码合入、发布、设备更新和实机验收分别报告。

普通 `update` 在 Mac 和 Windows 均先用原安装事务交接旧固定启动器，再激活新包；离线子进程检查必须能读取原活动包，原 policy、信任锚、固定解释器、暂停状态及其他 MCP 配置保持原样。本次分层源码只接受当前执行布局，0.3.0 专用兼容桥接已删除；旧安装可重新安装。中断后重试同一入口恢复已有 journal。

同一 update 入口还会安装或刷新全局 Hook，并自动登记和开启本设备所有项目的今后会话采集，包含旧设备和非交互更新。复用现有身份及服务，不补传历史；保留数据、队列、排除目录与隔离规则。代码 pin 与 inline command 沿用现有事务恢复；check-update 只报告状态。连接或登记失败保留原采集配置，重跑同一 update 恢复，不要求再次批准摘要或手填 profile ID。正常宿主 Hook 审核仍由用户处理。

## 诊断与证据边界

- 连接未完成初始化：`handshake / mcp-not-ready`。
- 当前 worker 没有提供某个工具：`tools-ready / tool-not-exposed`。核对 `tools/list` 与安装授权；工具缺失本身不能证明 Server 宕机。
- 工具已提供但读取失败：沿用既有 HTTP、传输、解析、远端错误与内容校验阶段；不将其归为工具未提供。
- 内容工具返回 `client_runtime.service_mode=approved-content`，表示工具所属内容服务，不能代替认证、采集或提炼证明。独立 synthetic sandbox 的成功不能证明正式服务成功。
- Hook outbox 的 `confirmed`、`core-accepted` 和事件 `committed` 只确认事件接收。`pipeline_state=unverified`、`model_extraction_verified=false` 明确表示模型提炼尚未确认；不能据此声称已有可查记忆。
- 对“刚才／本轮记录”的问题，需要匹配本轮的唯一标记，或在来源可用时核对事件、会话和发生时间。旧主题及 `memory_updated_at` 不能证明本轮采集成功；找不到证据就报告本轮未确认。

以上来源约束同时写入 MCP instructions 与读取工具描述；它不改变已加载的服务端 Skill，也不代表已验证真实模型一定遵循指引。初始化时的原生映射／身份访问仍有各自的失败与恢复边界；本回归隔离验证的是更新协调及 MCP 协议，不把合成结果扩大为所有启动阶段的端到端保证。

## 已授权 Content 对账与客户端自动升级设计

适用后续版本的 [#260](https://github.com/goodname427/agent-brain-client/issues/260) 和 [#261](https://github.com/goodname427/agent-brain-client/issues/261)。0.8.34 基线 `04eb957` 的正式 HTTPS MCP 固定启动器已在协商之外启动一次 `discover`，由 `ClientReleases.startup_check` 合并 60 秒内同策略的启动尝试。兼容版本已有同连接 worker 交接，MCP worker 空闲约 30 秒可退出，由原启动器继续持有连接。既有采集 `delivery.supervise` 在 worker 内，适合恢复采集队列。把新的定时触发只挂在那里时，闲置连接会漏掉 60 秒 Content 检查。

### 共享触发及状态

- 用持有宿主连接的固定启动器驱动两个任务，沿用现有受验证的短时子进程边界执行对账及升级操作。首个核验通过的连接立即触发 Content 检查，在 worker 停驻后继续调度。两个任务使用同一调度入口，各自有独立截止时间、尝试记录及设备内互斥。同一任务有执行者时跳过重复调度，释放调度状态锁后才做网络与原生文件操作，软件升级等待或失败时 Content 仍按自己的时钟执行。宿主均退出后由下次正常启动继续。
- 复用 `metadata.private_json`／`metadata.write` 的权属检查与原子保存，配合平台锁记录每项任务的上次尝试、上次成功和简短结果。活跃进程用单调时钟安排周期，持久状态和绝对暂停时刻用 UTC 时间。任务状态仅保存调度、授权绑定摘要和结果标识。软件升级策略独立于尝试状态、Content 授权及采集设置。配置缺失时默认为启用，明确关闭持续生效，暂停时刻到达后按已保存的启用状态运行。候选激活前重读策略和登记。用户界面提供启用、关闭、指定时刻和暂停一天。
- 用真实入口覆盖冷启动、进程重启、两个宿主争用同一设备、worker 停驻和更换后触发。测试把时钟和传输换成合成实现，模拟长时间更新同时 Content 照常运行。原采集队列继续由既有采集恢复入口服务。

### #260 已授权 Content 对账

- 健康时约每 60 秒检查，首次连接和已验证升级成功后立即触发。调度只认识最新通过校验的 Content 绑定，不枚举内容种类。解析现行登记、策略和已授权的 Content 类型及 ID，沿用分页 `content_catalog` 及快照校验。基线没有独立的授权版本接口，目录提交是快照一致性标识，条目 revision 可用于识别授权范围内的变化。比较时同时校验策略／服务绑定和映射是否已经应用，避免把另一个宿主的成功或一次失败尝试当作本地已应用。相同授权可复用目录检查结果，两个宿主分别持有自己的映射状态。
- 有变化时复用现有拉取校验与两宿主的映射事务，只获取改动条目的正文。MCP 协商外的定时任务先在既有队列事务和请求期限内重试待确认的原请求，再拉取最新目录。剩余待处理的本机写入和导入继续阻挡映射。单独的只拉取入口仍可跳过重放，显式拉取与写入继续沿用原语义。
- 基线拉取在 `content.lock` 内执行远端快照请求，离线 Content 读取也使用该锁。后台路径把有时限的目录和正文读取移到锁外，收到已知授权拒绝时独立持久化拒绝标记。只有在该标记之后取得并验证的新鲜快照才能再次用于离线读取。映射前以短时限获取原锁，重核当前授权、绑定、快照基线和队列／导入状态。观测到变化时下轮重取。映射写入、取消和异常恢复沿用原 journal。
- 合成验收在已协商连接中新增、修改和从活动目录归档 Rule 和 Skill，修改 Memory，验证授权排除、非托管文件、断线恢复、待写入原始字节及稳定目录无需读取正文。实际定时验收在没有 MCP 调用时推进时钟，验证只有一轮检查、生效快照及升级后立即检查；让合成 Content 网络停在快照阶段，验证新聊天、召回及既有离线读取仍可进行。已加载的模型上下文和磁盘映射分别取证。

### #261 客户端自动升级

- 将现有后台发布检查接入共用调度，在每台设备上将同策略的渠道检查合并到约一小时一轮。持有连接的启动器约每分钟核对任务是否到期或策略已恢复。复用已登记 stable 策略、`ClientReleases.update(lock_timeout=0, can_activate=…)`、`update.lock`／`python-write.lock`、健康检查、回滚及同连接交接。显式 `check-update`／`update` 继续走原入口，不读自动策略来决定是否执行。后台路径避开显式维护的 Hook 注册和采集设置工作。断线或锁忙保留当前可用版本，下一轮再试。
- `can_activate_at_startup` 已核对已登记的启动器、缓存 ABI 和工具契约。用相同入口确认各已安装宿主的有效契约。需要改登记、重新授权、重连或迁移的候选留给显式升级。保留在途请求，候选无法启动时沿用已获准的旧 worker，状态分别给出活动包、已观测运行版本以及未确认或待手动的原因。若首次功能版的固定启动器字节发生变化，0.8.34 原启动检查会拒绝这类候选的自动切换，由既有手动维护事务完成首次升级，缺省策略随新版本生效。
- 合成验收覆盖首次安装及旧版迁移、关闭跨升级不丢失、重启后暂停按绝对时刻到期、自动和手动竞争、离线下轮恢复、候选失败保留旧包及在途请求结束后交接。用 Content 仍对账且手动维护仍可用的证据核对升级关闭／暂停的影响。

## 合成验证

`tests/test_startup_concurrency.py` 使用隔离 HOME／USERPROFILE／CODEX_HOME、真实启动子进程及 MCP JSON 管道。阻塞合成发布源后，验证单会话、第二会话及 onboarding 更新加两个并发会话的 initialize 和 tools/list；检查同一批次只有一次发布源读取，更新后旧 worker 保持原版本，新 worker 选择新版。另覆盖未健康候选、首次安装无前版、读取竞争、包损坏、健康失败回滚、策略绑定冷却和握手／工具诊断。

同样的两个握手用例在未修改的 `52407ff` 上均超过 5 秒测试预算；这只是受控阻塞下的失败证据，不是实际设备的超时测量。修复后用例无需放开发布源阻塞即可完成握手。

事件回归继续使用原 Hook／outbox 类和合成回执，验证接收确认不会变成提炼确认。Mac 全套发现与 Windows Python 3.11／3.13 CI 显式执行新增并发模块。测试不读取真实记忆、不调用真实模型、不访问设备凭据、不复跑真实事件；用户设备上的正常新会话及真实模型使用验收另列。

## Windows 缓存权限兼容

全局采集旧入口先用普通 `mkdir` 创建 outbox 缓存，Windows 忽略 POSIX `0700` 并继承父目录 ACL；后续 `private_mode` 却只接受固定几个主体。已有缓存、暂存文件或持久锁带其他合法主体时也会在实际读写前被拒绝。设备报告的 `Windows item accessible to another principal` 与这条链路吻合，但缺少该设备实际 ACL 和 Hook 堆栈，不能断言它是唯一原因。

Windows 内容缓存现在交由系统决定实际读写权限，不再用主体名单作为准入门槛；缓存创建、暂存、队列、锁、worker 租约和安装状态读取使用同一边界。新建缓存目录、文件和锁沿用 Windows 原生继承权限，避免创建时又用固定主体名单覆盖系统／宿主授权；已有目录和锁的 ACL 不改写，不重置队列。文件类型、链接／reparse 检查、请求摘要、策略／身份绑定、原请求重试与并发互斥保持。凭据、代码包及配置策略仍走原严格校验，Mac 原行为保持。

原生 Windows 回归从已有普通目录和额外 ACL 出发，通过正式全局 Hook 暂存提示、生成离线 pending 事件、重启并重试原请求，核对原目录／锁 ACL 和已有资料保留。全局 Hook 错误的 stderr 增加 `operation_stage` 和 `error_type`，只报告阶段／类型，不输出正文或原始异常文本。

统一版本交付后最少实测：沿原入口更新一次；完成一个带唯一标记的新会话；检查这轮 `hook-turns` 和 outbox 的原请求及回执。若仍为空，保留现有状态并读取对应 Hook stderr 的阶段／类型；无需手改 ACL、重装、清空队列或补传历史。事件接收与模型提炼／召回分别核验；默认 Memory Query 的 `-32700` 属于独立问题，本修复不宣称解决。

## 正常更新中的后台交接

固定 MCP 启动器的前台交接和设备共享投递使用不同的租约。0.8.42 的独立投递进程可能在 0.8.43 已启用后继续占用 `worker.lock`。它会读取旧目录中的分页批次入口并报 `KeyError`，使新进程一直等锁。

新的分页批次入口保存在旧投递进程不会扫描的子目录。当前活动包检测到没有交接协议的进程时，暂存旧目录中的投递任务描述，让它完成已经开始的一轮并自然释放设备锁。等待进程使用同一把设备锁，验证活动包后恢复旧任务描述并继续扫描。原请求、批次进度、游标和回执始终留在原处。支持交接协议的进程在当前任务结束后响应换代。已进入网络的请求使用既有回执和稳定请求 ID 处理未知结果。

MCP `client_runtime` 和本地安装状态同时报告活动版本、实际投递版本与 `delivery_worker_status`。`legacy-running` 表示仍有旧进程但无法确认其版本，`handoff-pending` 表示正在换代，`current` 需要活动包版本和提交与实时投递租约一致。无活跃进程时显示 `idle` 或 `starting`。

独立回归见 `dev/integration/delivery_handoff.py`。它在临时设备目录运行正式 0.8.42 的投递代码和固定 MCP 启动器，通过公共更新及同一条 MCP 连接触发 0.8.43 复现和修复版接管。Windows CodeBuddy 来源布局在 Mac 上模拟，Windows 原生锁与 CodeBuddy IDE 另行实机验收。

## 共享后台投递与首字诊断

Codex 和 CodeBuddy 的新观察采用共同的前台顺序：可靠入队、唤醒后台、按当前问题召回。SessionStart 不等待旧队列恢复；上传失败或旧消息积压不应成为当前问题召回的前置条件。助手正文完成条件由各 Harness 验证，未完成正文不能入队为已完成消息。

后台复用原 request_id、event_id、时间和正文；未知回执不能更换请求 ID。当前身份、来源范围、暂停开关及 Server admission 在传输边界重新核验。MCP 启动恢复已登记来源的待处理工作，并在 MCP 存活期间监督脱离 Hook 的后台 worker；关闭所有进程或设备重启后，需要正常启动 Harness/MCP，不能宣称无进程时仍可上传。后台不安装系统服务、不修改用户启动项、不扫描历史会话。

全局后台投递在进入 outbox 前核对本地身份、来源和暂停状态。Server
admission 在 outbox 持锁读取原请求后和实际发送前重新核验。合成 pending
事件的状态请求由三次降至两次。发送前撤销授权时，原请求保留为 pending。

0.8.24 的首次安装可以从 `first-install/releases/packages` 启动后台 worker，而 `global-memory/code` 冻结副本可能尚未生成。原 worker 在读取队列和访问 Server 前即因冻结副本缺失而退出本轮，已入队事件持续 pending。独立启动的受管投递进程通过既有发布解析器确认自身是该设备当前可用的包，成功后复用该工作上下文。清单、列出文件及扩展布局成员校验沿用发布解析器的规则。每次投递仍重新检查来源批准、设备身份、队列和 Server admission。来源设置里的 Python pins 用于原生 Hook，允许早于当前投递包。独立冻结入口和 CodeBuddy 原生入口仍执行原有冻结校验。Mac 隔离回归走首次安装、原生 Hook、后台子进程及合成 Server 回执，检查原请求确认和再次启动后的去重。Windows 共用此后台入口，原生验证单独记录。

已授权的长消息按协议预算切分，所有分片保留原文，包括正文里的 LocalOnly 或限制共享字样。重试沿用已保存的分片边界和请求。历史排除记录继续生效。首条入队前原子保存完整观察的所有请求，分批中断或容量耗尽后由后台恢复原请求尾部；损坏日志按原字节保留到 `observed-review`，不阻塞其他合法事件。1,024 条容量只统计未解决请求，confirmed／reconciled 回执保留用于原请求去重。监督器从真实 pending／未完成观察刷新既有任务，项目入口在采集前保存固定设置的恢复路由。

召回准备完成不写输出去重标志。Codex／CodeBuddy CLI 在 stdout 成功 flush 后记录输出确认；此前中断允许同轮重新召回。stdout 与本地标志无法原子提交，flush 后、确认前中断可能重复提供上下文，不能承诺只输出一次，也不能宣称模型已采用。项目登记或采集失败仍执行当前问题召回。

Hook stderr 的 content-free 阶段计时区分初始化、本地入队、后台唤醒、召回和总耗时。CLI 总计时从 Python main 开始，不包含解释器启动、宿主 Hook 排队或模型首字等待；不能把它当作完整端到端首字指标。召回回执仍只证明上下文准备／输出，不证明模型采用。比较前后性能时需同设备同场景，分别记录冷／热启动、队列积压和并行会话；合成阻塞测试不替代真实耗时采样。

## 固定原生 Hook 入口

Codex 的批准与配置来源、事件和组／处理器位置绑定，也核验归一化后的命令和配置摘要。原实现把每次更新的代码目录和摘要写进命令。Mac 0.8.26 实测中，更新完成后原批准仍有效地指向旧命令，宿主因此在调用 AB 前跳过了三条新命令。这是 AB 更新体验问题。旧机制始于 0.6.2 的 #90。0.6.7 的 #97 开始原样保留宿主批准。

Codex 和 CodeBuddy 的全局和项目 Hook 共用固定入口。宿主批准的命令内含固定验证逻辑，通过已登记的 MCP 策略核验解释器，通过既有 MCP 登记的包摘要核验启动代码。设备私有目录中的独立启动脚本和摘要不参与授权。发行版本、包路径和代码摘要不进入宿主命令。核验后复用 MCP 的活动发行包选择、清单和事务校验。Windows 通过只有 ASCII 的 PowerShell `-Command` 解压命令内的固定载荷，给默认 `cmd.exe /C` 预留正常长路径的空间。用户路径保留在压缩载荷内，项目设置摘要留在原私有安装回执，项目范围、授权和暂停仍由原路径核验。

首次迁移后，现有发行事务回切到平台已发布且经验证的 0.8.26 时，固定命令照常使用选中的 0.8.26 入口，并输出去敏回切状态。兼容分支只识别这两个平台发行提交。保留的项目设置仍须满足 0.8.26 的项目约束。校验失败会保留宿主信任和设备状态并报告原因。

已登记的 Codex 命令原位迁移一次，原生审核由用户在宿主完成。更新结果保留 `native-review-required-for-new-command` 提示，产品不改宿主批准记录。普通代码更新保留已登记的 Hook 组、处理器索引和命令，宿主批准继续匹配。CodeBuddy 同样保留稳定命令和自定义权限，沿用它自己的宿主配置行为。两者的审核界面及实际加载由各自宿主决定。

设备默认目录及既有全局委托记录中、且带安装回执的项目会在普通更新时迁移。以前用自定义输出位置且未被登记的项目，沿用项目入口的 `install --settings ... --settings-sha256 ...` 执行一次迁移。该入口保留原项目暂停。外部改写或缺回执会保留待复核。

#316 的 Windows CodeBuddy 0.8.49 两次提交在 90 秒被宿主阻止。该版 CodeBuddy 的召回 socket 可独占 90 秒，且请求没有单独截止时间。设备日志缺少分段耗时，故两次现场超时的阻塞点仍未知。全局 CodeBuddy Hook 共用 29.4 秒客户端请求预算。前台持久记录和后台唤醒保留原有顺序，召回使用剩余预算。CodeBuddy 的新版登记包从 29.70 秒子进程预算扣除已用的活动包选择耗时，旧登记包保留时活动包的子进程从自身启动起计 29.43 秒。活动包还读取经验证的外层启动进程年龄，从 Windows PowerShell 启动起按 29.65 秒倒推剩余时间，Mac 从系统 Python 引导进程启动起按 29.75 秒倒推。无法读取时分别预留 0.85 秒和 0.35 秒。Codex 全局和项目的子进程截止时间分别为 115 秒和 28 秒。子进程超时时尽力输出一次空对象，已 flush 的结果原样保留。宿主输出管道即使阻塞也不延迟进程硬退出。超过截止时间才 flush 的结果不写成功确认。超时前已经落盘的队列继续靠现有恢复和监督器处理，未观察到收据时只报告未确认。

设置 `AGENT_BRAIN_RECALL_TIMING=1` 后，新版登记包的启动器在 stderr 另外记录活动发行包核验及子进程等待。 stderr 无法及时接收时，这些可选记录允许缺失，启动器仍可退出。已保留的旧版登记包仍可启动新版活动包，子进程预算来自活动包；启动阶段新计时则由实际登记包的版本决定。共享截止时间从登记包的启动函数进入时开始。PowerShell 和登记代码的前置检查、宿主调度和界面首显需单独计时。隔离回归还比较两份本地合成发行包执行同一条登记命令时的非 AB Hook 及 Codex 信任键与摘要。Windows 原生宿主执行与实际信任提示单独验收。
